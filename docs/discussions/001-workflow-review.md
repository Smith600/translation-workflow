   根据上述 hook 文档，可以给实施者一个**文档层面支持、尚未实测**的配置候选，而不必猜测普通版存在 `--no-tools` 参数：

   ```json
   {
     "hooks": {
       "PreToolUse": [
         {
           "matcher": "",
           "hooks": [
             {
               "type": "command",
               "command": "python3 -c \"raise SystemExit(2)\""
             }
           ]
         }
       ]
     }
   }
   ```

   这是在工具执行前一律拒绝，不是从模型可见的工具列表里删除工具；也没有使用会额外调用模型的 `prompt` hook。按文档，可再叠加对已知读写、执行及 MCP 工具的 `permissions.deny`。但单独依赖 hook 还不能称为失效即停止：文档明确说 hook 出错或超时会放行，因此后续实现必须验证 `-p` 下配置确实加载、阻断确实发生，并处理拦截器失效的情况。不能用“模型这次没有尝试调用工具”来验证权限有效。

   还需区分工具访问与启动时加载上下文。全局规则在每次会话启动时加载（`D/extensibility/rules.mdx:39-69`）；配置会合并，hooks 会从各来源收集（`D/reference/configuration/global-vs-local.mdx:142-160`）。`--config` 的存在并不能证明它关闭了其他导入。`read_config_from` 和 `subagents_enabled` 有明确文档（`D/reference/configuration/config-file.mdx:287-297,390-405`），可以作为实施时核对的配置项，但仍需核实最终有效配置。

   因而我的答复是：**有可核查的权限拒绝和全匹配执行前拦截机制；本轮没有证据把它升级为“当前普通 CLI 的 `-p` 全工具隔离已可靠验证”。** 我原先“使用专用配置”的建议应理解为实施方向，不能写成已完成的能力保证。在验证完成前，应保留“空目录运行＋提示约束，工具与上下文隔离待验证”的准确状态。
